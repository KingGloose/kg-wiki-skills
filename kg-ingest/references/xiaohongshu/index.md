# 小红书摄入

## 为什么是纯 HTTP，不用浏览器

小红书**单篇笔记页是服务端渲染**的，完整数据就在 HTML 的
`window.__INITIAL_STATE__` 里。所以：

- 不用调 API → 不用算 `x-s` / `x-t` 签名
- 不用 cookie、不用登录、不用 Playwright
- 分享链接自带 `xsec_token` 作为访问凭证

本质是「把你有权看的内容导出来」，不是爬虫。这和 `kg-zhihu` 必须走真浏览器
（`zse-ck` JS 挑战，带 cookie 都 403）形成对比 —— 别把两者的做法搞混。

参考实现：Obsidian 的 `xiaohongshu-importer` 插件也是这个思路
（`requestUrl` + 正则取 `__INITIAL_STATE__`），零认证。

## 边界：哪些能做，哪些不能

| 场景 | 可行性 | 走哪条路 |
|---|---|---|
| 单篇笔记 | ✅ 本 skill | 纯 HTTP 读 SSR |
| 搜索结果 | ❌ 不在 SSR 里（`feeds` 为空，前端异步拉） | 要 `kg-browser` |
| 我的收藏夹 | ❌ 个人数据，要登录态 | 要 `kg-browser` |

实测确认过：搜索页 HTTP 200 且有 `__INITIAL_STATE__`，但 `search.feeds` 是
空的。别浪费时间试纯 HTTP 抓搜索。

## 最大的坑：内容在图里

小红书是**图片媒介**。实测一篇 4800 赞的笔记，`desc` 字段全文只有：

```
#ChatGPT[话题]# #codex[话题]# #openai[话题]#
```

真正的信息在 6 张图里（3840x4864 的截图）。所以：

> **只存标题和话题 = 没存到东西。** 这样的页进知识库是噪音，
> 三个月后你看到只会困惑「我当时存这个干什么」。

### 图里的文字怎么提取：直接看，不装 OCR

`kg-media-to-text` 的图片 OCR 没有实现，**而且不打算实现**。

既然沉淀本身就由多模态模型在做，再装一层本地 OCR（rapidocr 之类）是多余的：
小红书图文常有标题层级、箭头标注、高亮框，OCR 出来是一堆散字且容易串行，
多模态能直接读懂版式和重点。

`--ocr` 参数保留着（底层库以后若补上就自动可用），但**正常流程不靠它**。

### 所以正确做法

抓完之后**直接把图读进来看**（`raw/<slug>/assets/` 下的文件），自己看懂再写
沉淀页。配合问用户一句：「这几张图我看到的是 X，你当时收藏它是因为什么？」
—— 用户的理由比图里的内容更值得记。

无论哪种，**沉淀页里要写清楚信息来源是图片**，别让人以为是原文照抄。

## 用法

本脚本只用标准库，不激活环境也能跑。但图片压缩要走底层库，所以统一用仓库的
环境入口（路径相对本 SKILL.md）：

```bash
# 基本：抓一篇存进 raw/
../../../bin/kg-py kg-ingest/references/xiaohongshu/xhs_to_md.py "<分享链接>" --out "<vault>/raw/xhs-<slug>.md"

# 图片放到指定目录（默认是 <out同级>/assets）
../../../bin/kg-py kg-ingest/references/xiaohongshu/xhs_to_md.py "<url>" --out x.md --assets "<vault>/assets"

# 不下载图片（只要元信息时）
../../../bin/kg-py kg-ingest/references/xiaohongshu/xhs_to_md.py "<url>" --no-images

# 看原始数据结构（调试用）
../../../bin/kg-py kg-ingest/references/xiaohongshu/xhs_to_md.py "<url>" --no-images --json
```

`kg-py` 自己找 venv，无需激活也无需 cd。也可以先
`source ../../../.venv/bin/activate` 再用 `python3`，效果一样。

链接从小红书 App「分享 → 复制链接」拿，形如
`http://xhslink.cn/o/xxxxx`。用户通常会连带那句
「复制这条信息，打开【小红书】App 查看」一起发过来，脚本会自己从文本里
找 URL，不用手动清理。

## 能拿到什么

```
标题、作者昵称、发布时间、note_id
正文 desc（图片笔记常为空）
话题标签（结构化，不是从正文里扒的）
互动数据：赞 / 藏 / 评
图片列表（原图，最大可达 3840x4864）
```

图片 CDN **无防盗链**，直连可下。下载后走 `media_to_text.compress_image`
压缩，但小红书的 JPEG 通常已经优化过，库会判断「压完反而更大」而保留原图 ——
这是正常行为，不是失败。

## 沉淀流程

1. **先查重** —— `kg-ask` 看库里是否已有。小红书内容同质化严重，
   同一个话题可能已经存过好几篇。
2. **抓取** —— 本 skill 落 `raw/`
3. **看图** —— 上面说的，这步不能跳
4. **确认再写** —— 报「标题 / 图里讲了什么 / 打算放 wiki 哪」，
   等用户点头。用户可能只想暂存 `raw/` 不要沉淀。
5. **写沉淀页** —— 注明信息来自图片；保留原链接（`xsec_token` 可能过期，
   过期后原链接打不开，图片已存本地所以内容不丢）

## 已知问题

- **`xsec_token` 可能有有效期。** 链接里带 `apptime` 时间戳。实测当天分享的
  链接可用，能存多久没测过。**建议用户分享后尽快处理**，别囤链接。
- **图片体积大。** 单篇 6 张图约 1.1 MB。批量摄入会让 vault 快速膨胀。
- **内容质量参差。** 小红书营销和种草内容多，信息密度普遍低于知乎。
  沉淀纪律应该比其他 skill 更严 —— 宁可不存。
- **视频笔记未测。** 脚本认 `type` 字段但没拿到视频样本验证。

## 失败排查

| 现象 | 原因 |
|---|---|
| 没有 `__INITIAL_STATE__` | 链接失效 / token 过期 / 笔记被删或转私密 / 小红书改成了客户端渲染 |
| `noteDetailMap` 为空 | 笔记不可见 |
| 落到 `/404?...error_code=300031` | 「当前笔记暂时无法浏览」——多半是 note_id 无效 |
| 图片下载 403 | CDN 策略变了（当前无防盗链，变了要加 Referer） |
