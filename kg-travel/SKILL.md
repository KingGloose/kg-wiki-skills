# kg-travel · 地图与出行

## 定位

给 AI 补上「位置感知 + 天气」能力。核心场景：

1. **天气查询**：实时天气 + 未来预报 + AQI + 紫外线 + 生活指数（晨练/穿衣/洗车/感冒/运动）——**要查天气优先用本 skill**
2. **地点查询**：地名 → 经纬度，经纬度 → 地名（逆地理编码）
3. **沿途发现**：某坐标周边 N 米内找美食/景点/酒店（按评分/距离/价格排序）
4. **路线规划**：A → B 的公交/驾车/步行/骑行方案（含坐哪路、几站、大概多久）
5. **导航跳转**：生成百度地图导航链接，用户点击直接导航到目的地（不用自己再搜）
6. **旅游规划**：把多个景点串成一条合理路线，沿途推荐吃喝

## 能力清单

| 子命令 | 用途 | 示例 |
|---|---|---|
| `weather` | 天气查询(实时+预报+AQI+指数) | `weather --city 海淀` |
| `navlink` | 导航跳转链接 | `navlink "故宫" --mode transit` |
| `geocode` | 地名→经纬度 | `geocode "天安门"` |
| `reverse` | 经纬度→地名 | `reverse "116.403963,39.915119"` |
| `search` | 按城市搜 POI（评分排序） | `search "烤鸭" --region 北京` |
| `around` | 周边检索（圆形区域） | `around "116.403963,39.915119" "美食"` |
| `transit` | 公交路线规划 | `transit "天安门" "颐和园" --city 北京` |
| `driving` | 驾车路线规划 | `driving "天安门" "颐和园"` |
| `walk` / `bike` | 步行/骑行路线 | `walk "天安门" "故宫"` |

**统一用法**：
```bash
python3 <skill>/scripts/baidu_map.py <子命令> <参数>
```
坐标统一 **lng,lat** 顺序传入（API 内部自动转 lat,lng）。

## 关键纪律

1. **坐标顺序**：所有 CLI 坐标参数都是 `lng,lat`（经度在前）。地理编码返回的是
   `lng/lat` 字段，传给路线规划时直接用。

2. **地名直接用**：`transit "天安门" "颐和园"` 直接传地名即可，脚本内部自动
   地理编码成坐标，不需要 AI 先手动 geocode 再传坐标。

3. **周边检索按评分排序**：`around` 默认 `industry_type:cater|sort_name:overall_rating`
   按评分降序。找「沿途好吃的」用它；找酒店用 `--industry hotel`；找景点/娱乐
   用 `--industry life`。

4. **定位来源**：用户的当前位置靠 **飞书位置消息** 获取——用户发位置（消息类型
   location），content 里有 `name/longitude/latitude`。拿到后转成 lng,lat 传脚本。
   飞书桥会自动把位置解析成 `[用户分享了位置：xxx，经纬度 lng,lat]` 注入上下文，
   看到这个就直接用坐标，不要重复问地址。拿不到定位就问用户在哪，不要瞎猜。

5. **选路原则**：多方案时优先展示公交（transit）——包含步行段、换乘站数、
   预计时间，信息最全。驾车/骑行按需。

6. **AK 不硬编码**：AK 在 `~/.kg-agent-config/credentials.json` 的 `baidu_map.ak`，
   脚本自己读。不要自己拼 API URL，不要尝试绕过脚本直接 curl。

7. **天气**：`weather --city 海淀`（中文/英文/区县编码都行）。报天气时除了温度，
   重点说 AQI、紫外线、降水概率、生活指数里的穿衣/运动建议——这些是百度
   独有的，比普通天气接口全。

8. **导航链接**：用户说「我要去 XX」「导航到 XX」时，用 `navlink "XX"` 生成
   链接直接给用户（飞书里点击即打开百度地图导航）。目的地支持地名或 lng,lat，
   默认公交 mode，可按需 driving/walking。起点默认「我的位置」（用户会在地图
   App 里自动定位）。

## 旅游规划工作流（多景点串联）

```
1. 收集景点清单（用户说/小红书攻略里提取）
2. 对每个景点 geocode 拿坐标（或直接传地名给 transit）
3. 相邻景点间 transit 规划（或 driving），估算每段耗时
4. around 每个景点周边找美食/补给点
5. 汇总成「路线 + 分段耗时 + 沿途推荐」规划报告
```

**排线原则**：
- 相邻景点按空间距离排（用 geocode 坐标算，或凭城市常识）
- 一天 3-4 个景点合理（含移动时间），太密不如舍掉
- 午餐点选在上午景点和下午景点之间（around 找美食）
- 公交优先（城市内），跨城用驾车

## 边界（做不到的）

- **实时公交到站时间**：百度无此 Web API。只有静态班次方案（坐哪路/几站/多久）。
- **用户 GPS 主动获取**：拿不到。靠用户主动发位置消息。
- **室内导航**、**路况实时播报**：不做。
- **天气逐分钟**：只有小时级预报（`forecast_hours`），没有分钟级。

## 常见坑

- `around` 和 `search` 不要用 `place/v2/search` 的 `location` 参数——那是精确匹配，
  返回 0 条。周边检索必须用 `around` 子命令（内部走 place/v3/around）。
- 百度 API 坐标是 **bd09ll**（百度坐标系），飞书位置消息给的是 **wgs84**（GPS 坐标）。
  直接用会有 ~几百米偏差。严格场景需要转换（gcj02↔bd09），日常场景偏差可接受，
  AI 在报告里注明「坐标可能有偏差」。
