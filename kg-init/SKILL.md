# kg-init · 把现有笔记改造成 LLM Wiki

典型场景：进到一个旧笔记仓库，**先用本 skill 改造，再用 kg-vault 注册路径**。

大多数人手上是**已有一堆笔记**——
散乱目录、Obsidian vault、导出的 Confluence 文档、几千张截图混在里面。
本 skill 负责把这些**归一化**成统一结构，好让其他 kg-* skill 能正常工作。

## 铁律：先讲清楚，再动手

**任何情况下都必须：先 `plan` → 讲给用户 → 等明确同意 → 才 `apply`。**

`apply` 不带 `--confirm` 会直接拒绝执行，这是脚本层面的保险。
但更重要的是**你要把计划讲明白**——尤其「为什么这么改」和「不会做什么」。
用户的笔记是多年积累的资产，不能让他觉得被 AI 随便动了。

## 三步流程

### 第 1 步：体检（只读）

```bash
cd kg-wiki-skills/kg-init && source ../.venv/bin/activate
python scripts/analyze_notes.py <笔记目录>
```

输出：笔记/文档/图片的数量与体积、领域分布、最大的笔记、非 md 文档清单、
未被引用的图片、现有双链数量、已有的 LLM Wiki 结构。

**把关键数字讲给用户**——他大概不知道自己有多少东西。
比如"你有 231 个笔记、6943 张图共 957MB，其中 216 张没被引用"。

### 第 2 步：出计划并解释（只读）

```bash
python scripts/migrate.py plan <笔记目录>
```

输出的计划包含四部分，**都要讲给用户**：

1. **为什么这么改** —— LLM Wiki 的唤醒+沉淀哲学，以及为什么选「整体归档」而非逐篇重写
2. **会做什么** —— 具体移动哪些目录、新建什么
3. **不会做什么** —— 不改内容、不删文件、不动 `.git`/`.obsidian`、不批量蒸馏
4. **风险与回滚** —— 是否 git 仓库、要不要先备份

**等用户明确说"可以"再进第 3 步。** 用户可能会想调整（比如某个目录不想归档），
这时和他讨论，必要时手动处理那部分再跑脚本。

### 第 3 步：执行

```bash
python scripts/migrate.py apply <笔记目录> --confirm --dry-run   # 建议先演练
python scripts/migrate.py apply <笔记目录> --confirm             # 真正执行
```

执行后**还有三件事要和用户一起做**（脚本故意不自动做）：

```bash
# 1. 生成 index 唤醒条目（需要判断，不能自动化）
python scripts/extract_topics.py <笔记目录>/archive
#    → 输出是草稿。你要做三件事再写进 index.md：
#      归并同类 / 删掉无价值的 / 压缩成可快速扫描的关键词行

# 2. 注册知识库，让其他 skill 能找到
python ../kg-vault/scripts/vault_cli.py add <笔记目录>

# 3. 陪用户改 AGENTS.md（templates/AGENTS.md 只是起点）
#    尤其「写作约定」和「领域划分」——那是最个人化的部分
```

## 与 kg-vault 的分工

```
旧笔记仓库 / 空目录
   ↓  本 skill（kg-init）   ← 建结构、从 templates/ 生成 AGENTS.md，先出计划让用户确认
标准的知识库结构
   ↓  kg-vault              ← 注册路径、切换默认
其他 skill 能找到它了
```

**模板在本 skill 的 `templates/`**（`AGENTS.md` / `index.md` / `log.md`）——
改模板 = 改所有新库的起点。

## 改造策略：整体归档 + 向前新建

```
改造前                      改造后
notes/                      notes/
├── 前端/                   ├── archive/          ← 原样封存，一字不改
├── 读书笔记/                │   ├── 前端/
├── 杂七杂八/                │   ├── 读书笔记/
└── 一堆图片                 │   └── 杂七杂八/
                            ├── wiki/             ← 新知识写这里
                            ├── raw/              ← 原始资料留档
                            ├── assets/           ← 新图片池
                            ├── AGENTS.md         ← 维护契约（最重要）
                            ├── index.md          ← 唤醒索引
                            └── log.md            ← 流水账
```

**为什么不逐篇整理？**

- 几百个文件逐篇重写不现实，**多半半途而废**
- 旧笔记是历史资产，原样保留比"整理得更好"更重要
- 真正的价值在**按需蒸馏**（just-in-time）：用到某篇时才把它升级成 wiki 页，
  那时你才知道该保留什么、补什么
- 旧知识不会消失——靠 `index.md` **唤醒**（知道 archive 里有什么）

## 各种笔记形态怎么处理

| 形态 | 处理 |
|------|------|
| 散乱的 md 目录 | 直接归档，最简单 |
| Obsidian vault | 归档笔记，**`.obsidian/` 保持在根目录不动**（配置还要用） |
| 导出的 doc/pdf/mht | 先归档；需要内容时用 `kg-doc` 转 Markdown 再沉淀 |
| 大量截图 | 跟着笔记一起归档。**不要清理未引用图片**——占比通常不大，风险高于收益 |
| 已经是 LLM Wiki | `plan` 会识别并只补缺失项，不覆盖 |
| git 仓库 | 提醒用户**先提交当前状态**；归档保留 git 历史 |
| 非 git 目录 | **强烈建议先备份**：`cp -a <目录> <目录>.backup` |

## 边界与注意

- **不修改任何笔记内容** —— 归档是移动，不是转换
- **不删除任何文件** —— 包括未引用的图片
- **不动工具目录** —— `.git` / `.obsidian` / `node_modules` 等留在根目录
- **不批量蒸馏** —— 那违背「一切按需」，且质量堪忧
- `apply` 是幂等的：已归档的不会重复移动，已存在的文件不覆盖
- 出问题看 `python scripts/migrate.py rollback <目录>`（会按 git/非 git 给不同方案）

## 已验证

- 拿一个真实 archive（231 个笔记、6943 张图、957MB、7032 处双链）跑 `analyze_notes`，
  数据准确，领域分布与最大文件识别正确。
- `extract_topics` 从 161 个文件抽出 2939 个标题，已过滤噪声标题（"总结"/"其他"/纯编号）。
- 模拟乱笔记目录（中文目录名、混 txt/png、有 `.obsidian`、git 仓库）全流程测试：
  `plan` 只读不动 → 无 `--confirm` 正确拒绝 → `--dry-run` 演练不落地 →
  `apply` 后内容原样、`.obsidian` 未动、log 已记录、结构被 `looks_like_vault` 认可 →
  重跑 `plan` 正确识别"无需归档"（幂等）。
